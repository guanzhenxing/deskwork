## 1. 产品定义

### 1.1 一句话与三种形态

Deskwork 是把资料变成成果的 AI 工作台：资料库、专家、技能、连接器围绕项目任务组织，产出可检查、可编辑、可交付的文件。产品逻辑全部在 DSH 引擎的插件层实现，以三种形态交付：

| 形态         | 用户     | 数据位置                                                                         | 产品组成                                 | 现状                                 |
| ------------ | -------- | -------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------ |
| 个人版（本地） | 单人     | 全部在本机 `~/.deskwork`                                                        | 桌面客户端（本仓库）                     | 在做；plan-v2 段一至三已完成          |
| 企业版（自管） | 组织成员 | 个人工作区默认仍在员工本机；组织内容、策略、审计汇总在组织自管的控制平面          | 同一桌面客户端 + 控制平面（独立部署物） | 未开始；闸门 G1（§6.3）              |
| 托管版（SaaS） | 注册用户 | 在我方服务器                                                                     | 服务器宿主 + 浏览器访问                  | 未开始；闸门 G2（§6.4）              |

三形态的关系是连续的：个人版的每一个工作台就是企业版、托管版的工作台——不换产品、不换数据格式，差别只在宿主与治理来源。这是本蓝图全部架构决策的出发点。

### 1.2 为什么按"个人 → 企业 → 托管"排序

1. **个人版是另外两种形态的组件来源**。按铁律二，产品全在插件层；企业版与托管版运行的是同一套工作台代码，只是宿主不同。先做完个人版，等于同时完成了企业版与托管版的全部功能面，剩下的只是治理与宿主工作。
2. **企业段的后进入者应当以长处进入**。MOVO 已用资金与先发占住"服务端优先"的位置（研究 §3：12 个 Docker 服务、多租户 Mongo、完整治理面）。与他们比拼服务端进度是以短击长；Deskwork 的长处在客户端：进程监督、恢复、Safe Mode、lease、准入、可复现打包（v1 §4.5，workdsh 与 MOVO 都没有），以及"企业采用不要求员工换工具"的连续性。
3. **托管版的能力台阶在企业版之后**。托管需要运维、合规、计费三样现在不存在的能力；企业自管版恰好是把治理能力先做成可交付软件的过程。中国市场上私有化部署是企业采购的常见前置（MOVO 的商业模式即由此而来），自管版先行符合需求顺序。
4. **个人版先可用，采用路径才存在**。企业采用的现实路径常常是员工先把本地工具带进公司，公司再采购治理能力。个人版免费可用是这条路径的入口（§7）。

三个被否决的替代方案：

- **立刻转企业段**：单人维护对上有资本加持、服务端完整的先发者，同时抛弃已完成 80% 的个人版地基。若在个人里程碑达成前出现真实的企业采用意愿，闸门 G1 可以提前触发——闸门按需求信号开，不按日历开。
- **永远只做个人版**（movo-research §4 结论 3 原案）：被 2026-09-29 决定取代。但该结论中"不牺牲本地产品、客户端不引服务栈"的论证有效，已转化为 §3 与 §9 的硬约束。
- **先做托管跳过企业**：在缺乏运维与合规能力时直接承接线上责任，且放弃了私有化需求明确的市场。

### 1.3 数据所有权承诺（分三级，如实表述）

| 形态     | 承诺                                                                                                       |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 个人版   | 数据在本机；出网流量只有模型调用与用户显式配置的连接器                                                      |
| 企业版   | 个人工作区默认仍在员工本机；组织得到的是策略执行、组织目录与审计汇总，而不是对个人全部数据的集中复制         |
| 托管版   | 数据在我方服务器；承诺可导出、可迁回本地版、可删除。**"数据在自己手里"在托管版不再成立，让位于"数据归用户所有且可带走"，必须向用户如实说明，不用模糊措辞掩盖** |

## 3. 不变的约束

### 3.1 三条铁律（继承 v1，三形态下价值放大）

1. **壳薄**：Electron 只做窗口、拉起本机服务、打包，不含产品逻辑。服务器宿主因此不需要重写产品。
2. **产品全在插件层**：所有功能是 DSH Profile 里的 cordis 插件。三种形态运行同一套工作台由此成立。
3. **上游零改动**：DSH 逐包 npm pin，`build/upstream-artifacts.json` 为单一事实源，`verify:dsh-closure` 对账不过不发版。引擎升级只有一条对账线，三种形态共用。

### 3.2 客户端安全模型红线（个人版与企业版桌面客户端同守）

- renderer 只加载 Host 发布的 authenticated loopback URL；Host-control 1.0 冻结协议是唯一的壳-引擎通道；
- 客户端不开任何入站监听；对控制平面只有出站 HTTPS（企业版新增，且是唯一的网络新增面）；
- home lease 防自己多开；home 准入按 data epoch 拒绝未知格式与不安全降级；
- 测试与冒烟只用隔离 `<testHome>`，绝不触碰真实 `~/.dsh` 与 `~/.deskwork`。

### 3.3 继承的既定事实（不重开）

home 为 `~/.deskwork` 且只认 `DESKWORK_HOME`；引擎跟随上游 rc（当前 `0.2.0-rc.1`）；从现有仓库代码生长、不重写；一次只改一件事、改完真跑；交付物为 `package:dir` 的 `.app`，不做 DMG（2026-09-29，清理为 plan-v2 步 7c）；包名 `@deskwork/*`、appId `local.deskwork.app`、Profile 名 `deskwork`。

## 4. 三形态统一架构

### 4.1 四个可移植地基

三形态共用的关键是把"随宿主变化的东西"收敛到四个接口稳定的地基上，先定契约、后做功能：

| 地基 | 内容 | 现在做什么（个人版） | 企业版形态 | 托管版形态 |
| ---- | ---- | -------------------- | ---------- | ---------- |
| F1 内核（身份/权限/审计） | principal 模型；资源-动作清单与 `read/write/dangerous` 三级风险标记；审计五元组（主体/时间/对象/动作/结果）事件 | 契约测试先行；本地后端（本地 principal、默认放行 + dangerous 确认、哈希链本地审计日志） | SSO principal；策略由平面下发（签名、缓存、离线降级可见）；审计日志批量上送（游标续传） | 租户 principal；同一契约，后端在服务侧 |
| F2 工作区可移植 | 工作区 = 一份 home 内的全部产品数据（资料与修订、技能、专家、任务与会话引用、设置）；引用一律相对路径；缓存与机器状态隔离在 home 的 cache/run 分区；导出/导入按 data epoch 版本化 | 落地为存储纪律（步 9、12 建库时生效）；导出/导入做产品化操作 | 员工本机工作区可整体纳入组织策略；组织目录下发不写入个人工作区 | 工作区在我方服务器，可整体导出迁回本地 |
| F3 无头运行纪律 | 每个工作台不得依赖 Electron 专属 API；deskwork Profile 可在纯 Node 进程内 boot 并提供官方 Web UI | 步 8b 无头启动冒烟，长期保持绿 | 同一个客户端 | 服务器宿主 = 同一 Profile 的服务器组合（研究 §2.2 已验证此路线服务端可行） |
| F4 能力治理接缝 | 模型按用途分槽（对话/视觉/嵌入/重排）；外部工具调用全部经连接器注册表（风险三级、审批语义、幂等键）；技能/专家 schema 带 `source_scope: personal/organization` | 模型槽位做本地偏好设置；注册表语义在步 14 落地；`source_scope` 字段在步 10/11 schema 一次定型 | 槽位与白名单由组织策略指派；组织目录按 scope 下发 | 我方网关承接模型槽位；目录同机制 |

**为什么现在就做内核（F1）不是为企业版提前付费**：个人版的活动流、每会话用量摘要、危险操作确认、office 交付物台账全部消费同一内核。契约定错再改，三形态一起返工；定对一次，三形态共用。F4 的模型槽位同理——对个人用户就是按用途控制成本与质量的设置项。

### 4.2 工作区与数据承诺的实现关系

数据承诺（§1.3）不是文案，是 F2 的验收：个人版导出的工作区，导入企业版客户端后策略照常生效；托管版导出的工作区，导入本地版后全部功能可用（不含组织目录与策略，它们不属于工作区）。导出/导入的往返校验进入对应段的验收标准。

### 4.3 控制平面（企业版的新组件，边界先行）

- **职责最小面**：身份桥接（OIDC）、策略下发（签名文档、版本化）、组织目录（技能/专家按 scope 分发）、审计汇集（游标续传）、模型网关（可选：组织自有 key 或代理）。企业版的配额、统计是平面侧对审计与用量日志的消费，不是客户端功能。
- **边界**：控制平面是独立部署物、独立仓库，在闸门 G1 通过后立项，不进本仓库；客户端对平面只有出站 HTTPS；平面失效时客户端以缓存的末次策略运行并明确提示，dangerous 级操作确认不因此跳过。
- **技术选型与部署形态是 G1 段设计评审的产出**，本蓝图只定上述边界与约束。刻意不从 MOVO 抄服务端栈：他们的 12 服务拓扑服务于其既有代码史，不构成我们的需求证据；平面从最小职责面出发选型。

| 14 连接器 | Streamable HTTP + 旧端点降级探测；`tools/list` 发现 + 按子工具白名单；schema 归一为 DSH 确定性子集，无法无损表达的构造按子工具拒绝并报告（不静默丢约束）；注册表带风险三级/审批策略/双模式超时/幂等键；会话内勾选 = 会话级能力快照；dangerous 级操作经 UI 审批确认后执行 |
| 15 office | 交付采用权威文件模式：产物作为权威文件落盘，模型只产出/修改工作副本；交付物台账登记来源会话、版本、校验和（消费 F1） |

### 5.3 生态接入

## 6. 路线：段与闸门

### 6.1 近期（plan-v2 承载，步序不变）

- 段三收尾：7c（DMG 摘除）。
- 段四 工作台与内核：**8 升格为内核三件套**（identity/access/audit，范围见 §4.1 F1，契约测试先行）；**8b 新增**（无头启动冒烟：deskwork Profile 在纯 Node 进程 boot、官方 Web UI 可达、工作台插槽在位——F3 的结构证明）；9–14 按原序；步 10/11 的 schema 携带 `source_scope`。
- 段五：15 office。
- 段四动工前落地插件层边界规则：产品插件包禁止直接 import `@deepseek-ai/*` 与壳层包，只准经 contracts 类型与 ctx 服务消费（采纳研究 §6.2 候选 1，把"单一适配层"原则交给机器检查）。

### 6.2 段六 · 个人版成品化（段四、五完成后）

打包与文档收尾；工作区导出/导入的产品化（F2 的用户面）；模型槽位设置界面（F4 本地面）；Windows 支持评估（产出成本清单：`build:native` 每平台构建、签名基础设施、冒烟矩阵扩展、lease helper 适配——只评估，不承诺时点）；在此段的观察期内确认真实使用信号，作为 G1 的需求证据。

### 6.3 段七 · 企业版（闸门 G1）

G1 进入条件（全部满足才开工）：

1. 个人版里程碑达成：工作台 + office + 成品化完成，打包产物日常可用；
2. 无头启动冒烟自步 8b 起持续为绿；
3. F1/F4 契约（五元组、资源-动作、风险三级、principal、source_scope、模型槽位）做过一次对照企业场景的设计评审并修订；
4. 至少一家真实组织表达采用意愿，且愿意共同设计；
5. 维护者容量决策：人力与资金到位，或显式接受缩小试点范围（单人开工的后果写明并接受）；
6. 商业许可初稿完成一次法律审查（§7）。

G1 交付：控制平面 v1（§4.3 最小职责面）、内核的企业后端（SSO principal、策略消费、审计上送）、组织目录分发、平面部署与安装文档、一个试点组织的实际运行一个观察周期。Windows 若为企业客户硬前置，在此段立项。

### 6.4 段八 · 托管版（闸门 G2）

G2 进入条件：G1 交付并经试点运行；运维手册、安全评审、事件响应流程存在；每租户成本模型（推理与存储）核算完成；定价与许可定稿；服务器宿主组合（同一 Profile 的服务器端 boot + host-control 监督）在隔离环境验证过——MOVO 的组合模式（研究 §2.2）是可行性参照。

G2 交付：多租户控制平面、服务器宿主、浏览器访问、计费、工作区导出迁回本地版的往返校验（§4.2）。

## 7. 商业与许可（建议，全部待维护者裁决）

- **客户端与插件（本仓库）建议保持 MIT 开源**：信任是本地优先产品的前提，也是"员工把工具带进公司"这条采用路径的入口；
- **控制平面与托管服务是收费位置**：企业版按席位年费（含平面、目录、支持）；托管版订阅；
- **平面许可形态待决**：若需要保护托管线，可参考 MOVO 社区许可中"禁止用我们的代码运营多租户 SaaS"这一条，但避免其非 OSI 许可的复杂性；G1 前完成法律审查；
- **个人版建议免费**：转化路径是采用路径（§1.2 第 4 条），收费会截断它；个人版用户即企业版的潜在采用者。

## 9. 明确不做

1. 画布/固定流程执行引擎——DSH Agent Loop 本身就是编排器，MOVO 也明确不做第二引擎；
2. 本仓库（客户端与插件产品）引入任何常驻服务端进程或入站监听——个人版与企业版桌面客户端同守此线；
3. 多租户、组织、配额计费进本仓库——这些只在控制平面（G1/G2 段、独立仓库）；
4. 检索授权取回后过滤——权限一律在查询期收敛（研究 §2.6 的隐患为证）；
5. 搬运 MOVO 代码——许可附加条款且技术栈无交集，只取架构决策；
6. 打包第二份浏览器、修改上游一行代码、产品名带 DeepSeek 品牌词；
7. 本地版做配额与计费——个人视角只观测不限制。
