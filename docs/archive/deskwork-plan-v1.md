# Deskwork 执行方案

- 状态：草案（经三遍审查修订）
- 日期：2026-09-28
- 相关：[蓝图](deskwork-blueprint.md)、[架构](architecture.md)、[开发指南](development.md)

## 1. 目标

把本仓库现有的 macOS 壳代码变成 **Deskwork**：一个数据在自己手里、引擎用 DSH 的本地 AI 工作台。

## 2. 已定的事

| 项 | 定 |
| --- | --- |
| 起点 | 仓库里现有的代码（112 个源文件、21,275 行、43 个测试文件）是起点，继续在上面长，不重写 |
| home | Deskwork 自己的应用数据目录，不指向 `~/.dsh` |
| 引擎 | `@deepseek-ai/dsh` 定到 `0.1.7-rc.2` |
| 节奏 | 一次只改一件事，改完真跑，做完停下 |

## 3. 保留、放弃、暂不动

**保留（继续用）**：`host-supervisor`（引擎启动与监督）、`desktop-contracts` 的 Host-control、`shell-core` 的失败分类与恢复会话、`profile-manager` 的修订事务、两个 bundle 作为插件写法样板、测试与隔离 home 夹具、staging 与打包链。

**放弃（要动代码，不是只改文档）**：

| 放弃的东西 | 代码上要做什么 |
| --- | --- |
| 跨产品格式准入 | 先把 launcher 与 CLI 的准入调用（`runHomeCompatibilityChain` / `admitHome`）替换成最小检查（marker 的 `schemaVersion` 与可接受的 epoch），再删 `inspect-home.ts` 的槽位勘察与 `preflightHome` 的判定树；launcher 侧 `admitHomeBeforeAnyWrite` 的失败分类要保留 |
| 公开发行证据链 | 先摘 `package.json` 与 CI 中的 script 引用，再删 `generate/verify-release-evidence`、`verify-artifacts`、`rehearse-upgrade` 与 `tests/upgrade/**`；`loadReleaseManifest` 被准入链使用，保留 |
| 与官方 CLI 共享 home 的并发叙事 | 只改文档与用户可见文案；lease 本身保留（防自己多开） |

**暂不动**：其余"可删"的东西一行不碰。它们不参与运行；等某个承诺明确不要了再删。

## 4. 工作分段

### 第一段 · 成为 Deskwork 并跑起来

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| 1 | 身份与 home 一次改完：`product-config` 的产品名与 userData 目录名、home 解析默认值、调用点 | 起来后数据落在 Deskwork 目录；`~/.dsh` 的 mtime 不变 |
| 2 | 引擎升到 `0.1.7-rc.2` | lockfile 里每个 `@deepseek-ai/dsh*` 都是 `0.1.7-rc.2`；类型检查过 |
| 3 | 真启动一次 | Host ready，官方 UI 挂载 |

第 2 步的第一个动作是 `pnpm install`。**这一步的真实规模以实测为准**，在 `pnpm install` 与类型检查跑出来之前不做任何估算。

### 第二段 · 第一个工作台可见

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| 4 | 读上游的 UI slot（侧栏入口）机制 | 能说出一个 bundle 注册侧栏入口的确切写法 |
| 5 | 写 bundle：侧栏入口 + 一个空面板 | 侧栏出现 Deskwork 入口 |
| 6 | 装上、启动 | 点进去是空面板，不是报错 |

第 4 步是必需的：本仓库现有的两个 bundle 只发布 surface，**没有注册过 UI 入口**；侧栏机制目前只有对参考项目的调研，尚未在本仓库验证。

### 第三段 · 打包前移

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| 7 | staging + 打包，得到可安装制品 | 装上能启动 |

打包前移到所有功能之前：后面的每个工作台都用**打包产物**验收，而不是只在开发入口里看着像对的。

### 第四段 · 工作台

按依赖顺序，每步一个可独立验收的插件：

| 步 | 工作台 | 验收 |
| --- | --- | --- |
| 8 | identity-local（本地身份） | 身份服务存在，且被后续工作台正确消费 |
| 9 | library（资料库） | 导入本地目录；修订钉死（源文件更新后历史引用不漂移）；检索与预览可用；配额与防护负例通过 |
| 10 | skills（技能） | 目录条目名与上游 loader 解析名的契约测试全绿（先写测试再动 UI） |
| 11 | experts（专家） | 发布冻结后不可变；旧发布可为新引擎重编译而不变异 |
| 12 | projects（项目） | 项目只聚合引用，不复制权威数据 |
| 13 | activity（活动流） | 展示原生任务与子代理活动；附每会话用量摘要 |
| 14 | connectors（连接器） | MCP 连接可用；会话内显式勾选生效 |

### 第五段 · 交付物层

| 步 | 做什么 | 验收 |
| --- | --- | --- |
| 15 | office 交付物层，按档推进：Word → PPT → HTML → PDF → 表格 | 每档按声明的标准做端到端往返校验；表格档标注实验性 |

## 5. 每步都照这四条做

1. 一次只改一件事，改完立刻真跑一遍。
2. 卡住就贴原始报错和行号。
3. 不确定的先花两分钟试出来；试不出来再问，只说清要对方定什么。
4. 做完一步就停，把真实结果摆出来。

## 6. 中止条件

- 第一段第 2 步：`pnpm install` 装不上，或类型检查的失败面超出"逐个修接口"的量级 → 停下汇报真实报错，不硬改。
- 第一段第 3 步：Host 在隔离 home 里起不来，且定位不到根因 → 停下，不带着起不来的引擎往下做。
- 任何一步触碰真实 `~/.dsh` → 立即停。

## 8. 评审记录

| 轮次 | 视角 | 发现并已修订 |
| --- | --- | --- |
| 1 | 事实与可行性 | "放弃格式准入"只写了结论、没写代码动作，而准入链接在 launcher 的恢复会话上，直接删会把启动链弄断 → 补成"先替换为最小检查，再删勘察"；"三条旅程走通"是口号不是验收 → 改为逐工作台的可测验收；计划正文把调研结论当成了事实 → 新增 §7 知识来源表 |
| 2 | 顺序与依赖 | 身份与 home 是同一处改动，拆成两步等于同一批文件改两遍 → 合并为一步；打包排在所有功能之后，导致后面每个工作台都只在开发入口里验收 → 前移为第三段；侧栏入口的机制本仓库从未实现过 → 在写 bundle 之前插入"读上游 UI slot 机制"一步；引擎升级的规模被写成已知 → 改为以 `pnpm install` 与类型检查的实测为准 |
| 3 | 风险与自欺 | 15 个步骤被列成等长清单，掩盖了量级差异（第 2 步、第 9 步、第 15 步各是数量级更大的工作）→ §7 标注了哪些是成熟工作、哪些是方向性内容；缺少中止条件 → 新增 §6；把继承自调研的阶段结构当成自己的方案 → §7 明确标注来源 |
